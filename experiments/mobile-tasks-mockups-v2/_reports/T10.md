# T10 — fix D1: phone permanently left-clipped at 320 px

## What was changed

One file: `experiments/mobile-tasks-mockups-v2/mockup.css`. Two edits, both in the shared
sheet; no HTML page was touched.

### 1. The fix — one new media query directly after the `.stage` rule

Before (`mockup.css`, the only layout rule involved — lines 189–200 pre-edit):

```css
.stage {
  min-height: 100vh;
  display: flex;
  align-items: center;
  justify-content: center;
  gap: 56px;
  flex-wrap: wrap;
  padding: 44px 24px 60px;
  background: ...;
}
```

After: the `.stage` rule is **byte-identical**; a scoped override was added immediately
below it:

```css
@media (max-width: 389.98px) {
  .stage {
    justify-content: flex-start;
  }
}
```

### 2. A header paragraph documenting the revision

A "Stage reachability (task T10)" paragraph was added to the file's top comment block,
matching the convention already used for the task 1.6b and T7 revisions. Comment-only.

## Why this approach, and why the suggested alternatives were rejected

Chosen: **a media query that applies only below 390 px**, switching `justify-content` to
`flex-start`. At 320 px the device row now starts at the stage's content-box left edge
(x = 24, inside the side padding), the phone occupies x = 24…414, and the page scrolls
right to reveal the rest — every pixel of the phone exists at x ≥ 0 inside the reachable
scroll area. Above the cutoff nothing at all changes (see next section).

Rejected:

- **`justify-content: safe center` on the base rule.** The phone overflows the stage's
  content box whenever the viewport is narrower than 390 + 48 px padding (438 px), and
  that includes 390 px itself — T9 measured the phone at x = −3 at 390 × 844. `safe`
  falls back to start alignment on overflow, so the phone would jump from its current
  flush position to x = 24 at exactly the 390 px width that must stay pixel-identical.
  It also leans on the `safe` keyword (Chrome 115+, Firefox 63+, Safari 11.x) which is
  adequate for a modern `file://` viewer, but moot since it fails the pixel-identity
  requirement anyway.
- **`min-width: max-content` on `.stage`.** The stage would become ≥ 438 px wide at every
  narrow width including 390 px, again moving the phone from flush to x = 24 at 390 px
  and adding a permanent horizontal scrollbar across the whole 390–437 px band. It also
  grows the stage's background box (the radial-gradient backdrop) past the viewport, a
  cosmetic change beyond the defect.
- **Auto margins on a content-sized wrapper.** Same start-at-24 geometry at 390 px, plus
  new markup on five pages — the most invasive option and still not pixel-identical.

The media query is the only option that fixes 320 px while leaving every width ≥ 390 px
under literally the same declarations as today. `flex-start` rather than `safe center`
inside the query: overflow always exists below 390 px, so `safe` would behave identically
to `flex-start` there, and `flex-start` has no support questions at all.

## Why 390 px (and up) rendering is unchanged

The added rule lives inside `@media (max-width: 389.98px)`. At any viewport of 390 px or
wider the media query does not match, so the cascade sees exactly the same `.stage`
declarations as before the edit — same specificity contest (none new), same values. The
base rule's text was not modified. At 390 × 844 the phone therefore still renders at
x = −3 with the screen at x = 6…378 exactly as T9 measured. 389.98 rather than 389 so
fractional layout viewports just under 390 px are also covered.

At 320 px, predicted geometry after the fix (6 px vertical scrollbar, as measured by T9):
stage content width 266 px, device pinned to the content-box left edge → phone x = 24…414,
screen x = 33…405, document scrollable width ≥ 414 → horizontal scroll range 0 … ~94
(was 0…38). Nothing sits at a negative coordinate, so the full phone is reachable.

## Containers checked — `.stage` is the only one

Verified by reading every page head and grepping the whole v2 directory:

- All five phone-bearing pages — `chrome.html`, `flow-1-list/index.html`,
  `flow-2-peek/index.html`, `flow-3-task/index.html`, `state-matrix/index.html` — put their
  `.device` elements **directly** inside one shared `.stage` (one `class="stage"` per page).
- `state-matrix` has no layout container of its own: its seven `.device` blocks are direct
  `.stage` children and its page-local `<style>` only styles `.themerow` (fixed-position,
  unaffected), `.devicecap a`, and `code`.
- `chrome.html` (two `.device` children) has no page-local `<style>` at all.
- No page-local stylesheet anywhere in v2 references `.stage` or overrides
  `justify-content`/`align-items` on any phone-bearing container (grep: zero hits).
- `index.html` has no `.stage` and no phone; its `.page` wrapper (`max-width: 880px;
margin: 0 auto`) is untouched and stays responsive exactly as today.
- One shared fix therefore covers all five pages, both themes, every parameter — no
  page-local overrides were added or needed.

## Vertical axis

`align-items: center` is deliberately untouched — requirement 4 (no vertical regression)
is satisfied by making zero vertical changes. Note for the record: the same class of
overflow-splitting issue can theoretically exist vertically at very short viewport heights
(phone min-height 620 px + caption vs `min-height: 100vh` stage), but T9 measured no
vertical defect at 844 px height and fixing it was out of scope for D1.
