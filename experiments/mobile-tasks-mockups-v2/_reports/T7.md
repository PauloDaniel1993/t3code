## A. The flow was broken in all three forward hops — FIXED

**Found.** Confirmed exactly as the punch list said:

- `flow-1-list` task/turn sub-row taps navigate to `../flow-2-peek/index.html?task=<id>`; flow-2
  read only `params.get("sheet")` → every row opened the default (mockups) sheet. (The turn row
  accidentally landed right because its owner _is_ the default sheet.)
- `flow-1-list`'s ↗ links and flow-2's "Open thread" / "Show in transcript" navigate to
  `../flow-3-task/index.html?task=<id>`; flow-3 read only `view` and `state` → every link
  rendered the mockups task regardless of id.

**Changed** (the alias approach from the brief — no emitter rewritten):

- `flow-2-peek`: accepts `?task=<id>` as an alias of `?sheet=` (`?sheet=` wins if both present);
  same value space (`task|apk|local|login|a4`). Devicecap documents the alias.
- `flow-3-task`: accepts `?task=task|apk|local|login` and renders that task (see B); unknown
  values fall back to the mockups task.
- `CONVENTIONS.md` §3 documents both (table below).

**Evidence.** `grep params.get(\"task\")` hits in both pages; the scripted check
(`flow-2 ?task= alias: OK`, `flow-3 ?task= select: OK`) passes; every emitted href now has a
reader that resolves it: flow-1 → flow-2 (`?task=`), flow-1 ↗ → flow-3 (`?task=`), flow-2
dismiss → flow-1 (`?peek=`, was already fine), flow-2 "Open thread"/"Show in transcript" →
flow-3 (`?task=`).

## B. The "four tasks, one page" lie — FIXED by modelling all four tasks

**Found.** flow-1 rendered ↗ "Open thread" on all four task rows (`?task=task|apk|local|login`)
and flow-2's sheet header did the same, but flow-3 modelled only the mockups task — three of
four links landed on a page showing a different task than the one tapped, with no indication.

**Decision: model all four** (option 1 of the three offered). Rationale: every fact needed
already exists in the scenario (CONVENTIONS §7.6) and in flow-2's `UNITS` — titles, creators,
contexts, states, turn rosters, durations, messages — so the pages can share one data source of
truth and no data had to be invented. Removing links (option 3) would have amputated the flow's
third hop; a "not modelled" notice (option 2) would have made flow-3 mostly a dead end.

**Changed.** `flow-3-task/index.html` now renders one of four task views, selected by
`?task=`:

- Each view is a `.taskview` wrapper (`display: contents`, page-local — only flow-3 needs
  per-task swapping) containing its own `.tbar` (back → that task's flow-2 sheet, title, state

  `flow-1-list?peek=<id>`, transcript, agent card where one ran), and `.composer-wrap`.
  `.taskview.hidden { display: none }` is declared page-local at higher specificity so it beats
  the promoted shared `.hidden` in the cascade (page styles load after the shared sheet).
- `view-task` (default): the existing mockups view, unchanged, still with its three `?state=`
  lifecycle tails/composers. `?state=` is documented as inert for the other three tasks.
- `view-apk`: **Done · 19m**, agent-created in _Fix T3 Connect Redirect Error_, fan-out plan,
  `.wcard` "Latest turn · 3 agents" — Locate Gradle wrapper + signing config ✓ 4m, Assemble
  release APK locally ✓ 11m, Verify install on emulator × `failed — tool-use budget exceeded`
  (names/durations verbatim from flow-2's `AGENTS_APK`; **no usage triples invented** — the
  scenario has none for this turn — and no `.wtype`, matching flow-2's own rendering of these
  rows), the Result message, `.evt.wake` "Returned to the parent — woke Fix T3 Connect Redirect
  Error", enabled "Message this task…" composer.
- `view-local`: **Done · 59s**, created by **you** from 2 selected messages (iconless
  provenance — the asterisk is the agent glyph; no icon invented), the "Yes — Gradle wrapper…"
  answer, wake event, no agent card (none ran — no counters at all), enabled "Message this

- `view-login`: **Working · 24s**, created by **you**, the pairing-token progress message,

- All four: overflow menu + Attach + send toasts (class-based `.js-menu` / existing ids), theme
  preserved across all links via the existing `data-to` rewrite.
- `?view=parent` now redirects to `flow-1-list?peek=<current task>` (was hardcoded `peek=task` —
  with four tasks that would have been the same class of lie).

## C. Disabled-composer contrast defect — FIXED in `mockup.css`, re-measured

**Found.** `.sh-composer.disabled { opacity: 0.65 }` composited the §7.2-mandated reason
sentence toward the background: the mandatory text measured **2.6492:1 dark / 2.5460:1 light**
on the sheet composites (recomputed, WCAG 2.x luminance method from CONTRAST.md). flow-2 had a
page-local `opacity: 1` workaround; state-matrix did not, so both its disabled composers
(`cancelled`, `native`) rendered the reason at the failing ratio. flow-3's page-local
`.composer.disabled { opacity: 0.65 }` had the same defect on its card surface (**2.6439:1
dark / 2.6410:1 light**).

**Changed.** `mockup.css`: the opacity declaration is gone (with a comment explaining why).
The disabled read is carried by the already-shared greyed send pill
(`.sh-composer.disabled .sh-send` → `--border2` bg, `--dim` glyph) plus the `--dim` note at
full strength — exactly how flow-2's workaround read. flow-2's override and flow-3's dimmed
`.composer.disabled` were both deleted; the promoted `.composer.disabled .send` (item D) greys
the standalone composer's send with **no** opacity anywhere.

**Re-measured (after):** reason note now at full-strength token values — dark sheet composite
**4.6921:1 PASS**, light sheet composite **4.9126:1 PASS**, dark card **4.6583:1 PASS**, light
card **5.2820:1 PASS**. The greyed send glyph (non-text, WCAG 1.4.11 3:1 min): **3.1999:1
dark / 3.3832:1 light PASS** — and its meaning is carried by the adjacent sentence per §7.2.
All recorded in CONTRAST.md's new effective-contrast section.
