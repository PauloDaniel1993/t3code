# Verify Kimi Code on Windows

Use this acceptance procedure with a working Kimi Code installation, a disposable project, a separate authenticated Kimi home, and an isolated T3 environment. Record the CLI version, executable path, T3 home, and results. Restart only that test environment. This procedure does not require changing a real T3 database.

T3's provider logs are under the test environment's state directory, `logs/provider/events.<thread-id>.log` (and rotated siblings). With an explicit T3 home, that is `<T3 home>/userdata/logs/provider/`. The logs record request methods and summarized payloads, rather than raw configuration values. Use the probe below for raw setup presence and option metadata, and observable tool/file behavior for approval and plan checks.

1. **Identify the executable.** Run `where.exe kimi`, then the selected executable with `--version`. Confirm it is Kimi Code: the npm `kimi.cmd` shim, WinGet link, or native `.kimi-code/bin/kimi.exe`. Set the Kimi provider's Binary path explicitly if multiple commands are installed. Record the path and version.
2. **Check status and update.** Enable **Kimi** in Settings and refresh. Expect ready, authenticated, and the version from step 1. Check that the offered update uses the owning package manager: npm or `winget upgrade --id MoonshotAI.KimiCodeCLI`. Native Windows installations require the installer in the [Kimi user guide](../user/kimi.md). When an update is available, run the applicable action on the test installation, rerun `--version`, and refresh status; both must show the new version. If no update is available, record update execution as unverified.
3. **Check separate sign-in.** Set KIMI_CODE_HOME path to an empty test directory and refresh. Expect not authenticated and guidance to run `kimi login`. In PowerShell, set `$env:KIMI_CODE_HOME` to that directory, invoke the executable from step 1 with `login`, then refresh. Expect ready. Verify the original Kimi home was not modified.
4. **Run the compatibility probe.** Follow the optional probe section below using the executable and home from steps 1–3. Expect visible `Kimi ACP compatibility observations`, ACP 1 or 2, and native resume or load support. Record authentication-method types, image support, MCP capabilities, raw resume `configOptions` presence, and model/mode option `id`, `name`, and `category`.
5. **Discover model IDs.** Open a Kimi thread and send a short turn. Expect models and thinking options in the picker, with no separate Mode picker or autonomous option. From a Codex or Claude thread, ask the agent to call `task_models` after ticket 30 is integrated; before that, use `orchestrator_capabilities`. Record a non-default Kimi model slug from the tool result and its displayed name. Use the slug in later delegation requests. New accounts and newly added models need fresh Kimi conversation discovery before named-model delegation is accepted; a removed-model failure also republishes fresh discovery. Status refresh alone does not discover models.
6. **Check approvals.** Under approval-required, ask Kimi to run `git status`. Expect an approval card containing `git status` without `Requesting approval to Running:`. Decline and check that no command output or execution appears. Repeat under full access and expect automatic approval with command output. Locate that thread's provider log and record successful `session/set_config_option` requests. Native mode values are summarized in these logs; confirm supervision through the actual approval exchange. The interaction probe records `approval-prefix:true` or `false` without printing the permission text.
7. **Check plan and implementation.** Ask Kimi to plan a change to a disposable file. Expect no executed tools and unchanged files; inspect `git diff` and the thread's tool events. Then request implementation in normal mode. Expect the change and tool events, without remaining stuck in planning. Check the provider log for configuration requests before each prompt. An unavailable read-only plan mode must produce a readable failed turn with no `session/prompt` request. Once ticket 28's carry-over is integrated and a migrated thread with an old saved plan selection is available, repeat a normal turn there and confirm it can implement; record that check as dependent on ticket 28 otherwise.
8. **Check questions.** Ask Kimi to ask a scope question, including under full access. Expect a question card that accepts an answer. Use the thread's provider log or the interaction probe to record `AskUserQuestion` permission handling or `session/elicitation`. The probe cancels its questions and approvals.
9. **Check cancellation.** Note the test T3 process and its Kimi/tool child PIDs in Task Manager or Process Explorer. Start a long turn and stop it. Expect interrupted status and no continuing tool work. Close the test session and check that its recorded process tree leaves no leaked child processes. Do not stop processes by matching names or paths.
10. **Delegate immediately after restart.** After step 5, restart the isolated T3 environment. Before opening or sending a turn in any Kimi thread, ask a Codex or Claude agent to delegate to `driverKind: "kimi"` with the recorded model slug. Expect the child to start and report its result without a model-not-advertised error. A new account without a saved catalog needs step 5 first.
11. **Resume a chosen model, then test plan and switching.** Select the non-default model in a Kimi thread, send a turn, restart the isolated environment, and send another turn in that same thread. Check its provider log for `session/resume`, or `session/load` on a load-only CLI. Expect completion with the same chosen model and no duplicate history. If the probe showed config-free resumes, expect the catalog to remain available and no model-reselection request. Now request a plan turn under full access: with no reported modes, expect the readable refusal, no new `session/prompt`, no executed tools, and unchanged files. Try switching models in that resumed thread: with no model-switch capability, expect a refusal rather than a changed label with the old native model. Delegate with the recorded model afterwards and expect a result.
12. **Check failure diagnostics.** In the disposable environment, reproduce an available provider error, such as a failed network request. Expect failed status and a redacted reason. Compare with `<KIMI_CODE_HOME>/sessions/<native-session-id>/logs/kimi-code.log` and its `acp: turn ended with failed reason error=` entry. If no provider error can be reproduced, record this check as unverified. Do not share credentials from logs.
13. **Check images.** Attach a PNG with a simple identifiable subject. If the handshake advertised image support, ask Kimi to identify it and confirm the image prompt completed. Without advertised support, expect a clear rejection before the prompt reaches Kimi.
14. **Check helper generation.** Select Kimi as the system model and generate a thread title, branch name, commit message, and change request description. Expect valid output, no tool execution, and no remaining `%TEMP%/t3-kimi-text-*` workspace after each operation. Native helper session records may remain in the test Kimi home.
15. **Check delegation and the MCP bridge.** Delegate from Codex or Claude with the model omitted, then with the recorded model slug. Expect both children to run and report results. In a child, ask Kimi to call `t3_environment_read` and quote one returned field; verify the actual tool event and result. Record whether the CLI accepts T3's stdio MCP bridge together with the handshake's `mcpCapabilities`; HTTP support alone does not establish stdio support. An unsupported `delegate_task` option `options: [{id: "reasoningEffort", value: "high"}]` must return `invalid_request`. After ticket 30 is integrated, call `task_create` with `title`, `prompt`, `context: "none"`, `model: {instanceId: "kimi", model: "kimi-default"}`, and `reasoning: "high"`: for a model with no select reasoning levels, expect `invalid_request` with "has no reasoning levels" and no child created. Confirm the exact instance ID and reasoning levels using `task_models` first.
16. **Inspect the process environment.** In Process Explorer, inspect the Kimi child belonging to the test environment. Confirm `KIMI_CODE_NO_AUTO_UPDATE=1` and the configured `KIMI_CODE_HOME`.
17. **Check the Windows shell.** Request a harmless shell tool and expect output and a completed turn. If shell discovery fails, set `KIMI_SHELL_PATH` in the provider instance's environment to the shell's absolute executable path and retry. Record the shell path and result.

## Optional CLI probe

From `apps/server` in the source checkout, use the package's own binary and explicitly opt in:

```powershell
$env:T3_KIMI_ACP_PROBE = "1"
$env:T3_KIMI_CODE_HOME = "C:\path\to\authenticated-test-home"
# Set this when Kimi Code is not the default executable on PATH:
$env:T3_KIMI_BINARY = "C:\path\to\kimi.cmd"
./node_modules/.bin/vp test run src/provider/acp/KimiAcpCliProbe.test.ts
```

Expect a passing authenticate/create/prompt/resume check and visible, redacted `Kimi ACP compatibility observations`. The probe uses the live console and clock, a temporary workspace, no requested tools, and no MCP servers. It does not verify the child's MCP bridge; use step 15 for that. Its native sessions may remain in the test Kimi home.

Set `$env:T3_KIMI_ACP_INTERACTION_PROBE = "1"` and repeat to request question and permission exchanges. Every observed request is cancelled; only shape metadata and the approval-prefix boolean are reported. Remove the probe variables afterwards:

```powershell
Remove-Item Env:T3_KIMI_ACP_PROBE, Env:T3_KIMI_ACP_INTERACTION_PROBE, Env:T3_KIMI_CODE_HOME, Env:T3_KIMI_BINARY -ErrorAction SilentlyContinue
```

Without `T3_KIMI_ACP_PROBE=1`, the test stays skipped and never launches Kimi.
