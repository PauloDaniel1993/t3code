# Flow persistence and recovery

Flow-run state belongs in fork tables rather than orchestration events: the graph, attempts and approvals are fork-owned state, while threads and turns retain upstream orchestration semantics. Keeping the link in indexed fork tables avoids extending upstream event schemas or replaying flow transitions into thread projections. Resolve thread membership through `flow.runForThread`; ordinary threads need no flow subscription.

Recovery must coordinate with thread auto-continue instead of launching a second agent turn. A recovered agent step keeps waiting when its existing turn auto-continues; if auto-continue is disabled, exhausted or skipped, the step fails as `interrupted`. Commands cannot be resumed after restart and fail as `interrupted`; approval steps keep waiting. Persist the chosen step thread id before launch and serialize transitions per flow run, so recovery and a late completion cannot launch the same step twice. See the [flow engine](../../apps/server/src/flows/FlowEngine.ts) and [repository](../../apps/server/src/flows/FlowRunRepository.ts).
