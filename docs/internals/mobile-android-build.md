# Building a standalone Android APK

How to produce an installable APK of `apps/mobile` that runs **without Metro** — JS
bundle embedded, Hermes, no dev server. Verified working on Windows 11.

For day-to-day development against Metro, see
`docs/internals/mobile-expo-dev.md`.

## Dev client vs standalone

These are different artifacts and the distinction causes repeated confusion:

|                         | dev client                                               | standalone              |
| ----------------------- | -------------------------------------------------------- | ----------------------- |
| Variants                | `development`, `preview:dev` (`developmentClient: true`) | `preview`, `production` |
| JS bundle               | fetched from Metro at launch                             | embedded in the APK     |
| Works offline / off-LAN | no                                                       | yes                     |
| Gradle task             | `assembleDebug`                                          | `assembleRelease`       |

If the app opens to a "looking for a bundler" screen, you built a dev client.

## Prerequisites

Local Android builds need an SDK **and** an NDK — the app compiles several native
modules from source. Requirements pinned by the project:

```
compileSdk 36 · build-tools 36.0.0 · NDK 27.1.12297006
AGP 8.12.0 · Gradle 9.3.1 · Kotlin 2.1.20 · JDK 21
```

Plus, for reasons in "Known failures" below: **JDK 17** and **CMake 3.31.6**.

`eas build --local` does **not** run natively on Windows (it wants WSL). Drive
`expo prebuild` and `gradlew` directly instead — that path is proven here.

## Build

```bash
cd apps/mobile

# 1. Generate the native project (android/ is gitignored)
APP_VARIANT=production ./node_modules/.bin/expo prebuild --platform android

# 2. Re-apply the generated-file Gradle fixes (see below)

# 3. Build
cd android && ./gradlew assembleRelease
```

Roughly 10 minutes for a full release build. Restricting ABIs to `arm64-v8a` cuts
that substantially and is fine for a modern test device.

**Do not use the `android`, `android:dev`, `android:prod` npm scripts for this.**
They run `expo prebuild --clean`, which regenerates `android/` and wipes the fixes
in step 2 every time.

## Known failures, and why they happen

All four are Windows + pnpm interactions. None are caused by this repo's code.

### 1. foojay / `JvmVendorSpec.IBM_SEMERU` — `NoSuchFieldError`

`@react-native/gradle-plugin` is an included build that compiles itself with
`jvmToolchain(17)`. With only JDK 21 installed, Gradle tries to auto-provision a
JDK 17 through the foojay resolver **0.5.0** it pins, and foojay 0.5.0 references
`JvmVendorSpec.IBM_SEMERU`, which Gradle 9 removed.

**Fix — machine level, persists.** Install Temurin JDK 17 and register it:

```properties
# ~/.gradle/gradle.properties
org.gradle.java.installations.paths=C:\\Users\\<you>\\.gradle\\jdks\\jdk-17.0.20+8
org.gradle.java.installations.auto-download=false
```

Dropping the JDK into `~/.gradle/jdks` is **not** enough on its own — Gradle does
not auto-detect it there, so the explicit path property is doing the work.
`auto-download=false` is deliberate: a future missing toolchain then fails with a
clear message instead of crashing inside foojay.

This lives at user level rather than in the project because `android/` is
regenerated by prebuild. The tradeoff is that it applies to every Gradle build on
the machine.

### 2. `expo-updates` NDK mismatch — ninja regenerates forever

`expo-updates` does not inherit `rootProject.ext.ndkVersion`, so it falls back to
AGP 8.12's default NDK (`27.0.12077973`) rather than the pinned `27.1.12297006`.
Every file under the nonexistent NDK path reads as dirty, CMake regenerates in a
loop, and ninja gives up after 100 tries.

**Fix — generated file, must be re-applied after every prebuild.** Pin `ndkVersion`
for all subprojects.

### 3. `.cxx` paths ≥ 250 characters — ninja cannot `stat` files that exist

pnpm's hashed virtual store produces paths like:

```
node_modules/.pnpm/react-native-screens@4.25.2_f004341eb.../node_modules/
  react-native-screens/android/.cxx/Debug/3g461f5s/prefab/arm64-v8a/...
```

The prefab config files are really there, but ninja 1.10 is not long-path aware,
its `stat` fails, it calls them missing, and loops.

Note `LongPathsEnabled=1` and `core.longpaths=true` do **not** help — a binary that
does not opt in is unaffected. The `CMAKE_OBJECT_PATH_MAX` warning is also a red
herring; modules fail this way without emitting it.

**Fix — generated file, must be re-applied.** Relocate each module's native staging
tree to a short root, e.g. `C:/t3cxx/<module>` (~120 chars instead of ~250).

### 4. Codegen C++ at 273 characters — not relocatable

This one is generated source inside the pnpm store, so it cannot be moved.

**Fix — machine level, persists.** Use **CMake 3.31.6**, whose ninja 1.12.1 _is_
long-path aware. Verified directly: ninja 1.10 fails on that exact file, 1.12.1
builds it. Make sure the build selects 3.31.6 if 3.22.1 is also installed.

With this in place there is no need to build from a short drive root — the
path-length constraint is gone.

## Applying the generated-file fixes correctly

Fixes 2 and 3 go into `apps/mobile/android/build.gradle`, which prebuild
regenerates. One detail matters:

**`subprojects { afterEvaluate { } }` does not work.** `expo-root-project` eagerly
evaluates the autolinked modules _during_ root evaluation, so by the time any block
placed after it runs, those projects are already evaluated and `afterEvaluate` is
rejected. Reordering is not reliable either.

Use a `gradle.afterProject` lifecycle hook **registered before the plugin
applications** — it fires as each project is evaluated, regardless of ordering.
Guard it with an `os.name` Windows check and comment why it exists.

**Durable fix, not yet done:** move both into an Expo config plugin alongside
`apps/mobile/plugins/withAndroidGradleHeap.cjs`, so prebuild emits them and
`--clean` stops being destructive.

## App variants

`app.config.ts` holds a `VARIANT_CONFIG` keyed by `APP_VARIANT`, each entry
carrying its own `appName`, `scheme`, and bundle/package id — so variants install
side by side:

| variant       | name            | package                      |
| ------------- | --------------- | ---------------------------- |
| `development` | T3 Code Dev     | `com.t3tools.t3code.dev`     |
| `preview`     | T3 Code Preview | `com.t3tools.t3code.preview` |
| `production`  | T3 Code         | `com.t3tools.t3code`         |

Adding one means extending `VARIANT_CONFIG`, the `AppVariant` type, and the
`resolveAppVariant` switch.

## Disable OTA updates before building a release

The committed config points `updates.url` at **upstream's** Expo project with
`checkAutomatically: "ON_LOAD"`:

```ts
updates: { enabled: true, url: "https://u.expo.dev/d763fcb8-…", checkAutomatically: "ON_LOAD" }
```

A release APK built with that intact will **fetch upstream's bundle over yours at
launch**, silently replacing the code you just built. Set `updates.enabled: false`
for any local release build. This is the single easiest way to ship an APK that
does not contain your work.

## Signing

Local release builds here use the **Android debug signing certificate**. They
sideload normally. The consequence is that an app previously installed with a
different certificate (e.g. an EAS-signed build of the same package id) must be
uninstalled first — signatures cannot be swapped in place.

A production keystore is only needed for distribution, not for sideloading.

## Verifying an APK really is standalone

Do not assume. Check:

```bash
unzip -l app-release.apk | grep index.android.bundle   # embedded JS, expect ~19 MB
aapt2 dump badging app-release.apk | head              # package, label, launcher
apksigner verify --print-certs app-release.apk         # signature
```

Also confirm `android:debuggable` is **absent** from the packaged manifest and that
OTA updates are disabled in it. A reference successful build produced a 192 MB APK
across four ABIs with a 19,250,696-byte embedded bundle.

## Install

```bash
adb install -r apps/mobile/build/<name>.apk
adb shell pm list packages | grep t3tools
```

A distinct package id installs alongside existing builds without replacing them.

## Artifacts left on the machine

Local Android builds create things nothing in the repo cleans up:

- `C:\t3cxx` — relocated native build output
- `~/.gradle/jdks/` — the extra JDK 17
- `apps/mobile/android/` — generated, gitignored

Worth knowing when disk space matters; they are several GB combined.
